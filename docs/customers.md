# مدیریت مشتریان

صفحه `/page/customers-page.html` از سیستم ورود فعلی و APIهای FastAPI استفاده می‌کند. تمام اطلاعات مشتری در جدول `customers` ذخیره می‌شوند و شماره اول آرایه JSON شماره اصلی است. ثبت و ویرایش بدون شماره نیز مجاز است.

## اجرا

```sh
python3 -m pip install -r backend/requirements.txt
npm install
npx tailwindcss -i ./src/input.css -o ./src/output.css
python3 start.py
```

`npm run dev` کامپایل Tailwind را در حالت watch اجرا می‌کند. سرور Frontend روی `127.0.0.1:5501` و Backend روی `127.0.0.1:8000` است.

مسیر پیش‌فرض دیتابیس طبق معماری موجود `~/.karbon/karbon.db` حفظ شده است. متغیر اختیاری `KARBON_DATABASE_PATH` مسیر دیتابیس را برای محیط توسعه یا تست تغییر می‌دهد؛ مسیر والد باید وجود داشته باشد. جدول مشتریان با `Base.metadata.create_all` ایجاد می‌شود و جدول کاربران یا داده‌های قبلی بازنشانی نمی‌شوند. secret مربوط به JWT همان تنظیمات فعلی در `~/.karbon/.env` است.

## قرارداد API

همه درخواست‌ها به Bearer token موجود نیاز دارند.

| روش | مسیر | کاربرد |
| --- | --- | --- |
| GET | `/api/customers?search=&skip=0&limit=50` | جستجو و دریافت دسته‌ای؛ خروجی `items`, `total`, `skip`, `limit` |
| GET | `/api/customers/next-code` | پیش‌نمایش کد مشتری |
| GET | `/api/customers/{id}` | جزئیات و خلاصه آماری |
| POST | `/api/customers` | ثبت؛ پاسخ ۲۰۱ |
| PUT | `/api/customers/{id}` | جایگزینی اطلاعات قابل ویرایش |
| DELETE | `/api/customers/{id}` | حذف؛ پاسخ ۲۰۴ |

کد فقط در Backend، داخل تراکنش دارای `BEGIN IMMEDIATE` تعیین می‌شود. پیش‌نمایش کد ممکن است در صورت ثبت هم‌زمان تغییر کند؛ پاسخ ثبت، کد قطعی است. کدهای نمایشی از ۱۰۰۱ شروع می‌شوند و پس از حذف، باقی‌مانده‌ها به ترتیب ثبت دوباره بدون فاصله شماره‌گذاری می‌شوند؛ کد مشتری بعدی برابر ۱۰۰۱ + تعداد مشتریان است. شناسه داخلی هر مشتری ثابت می‌ماند و دوباره استفاده نمی‌شود. کد حساب درآمد در تراکنش‌های مرتبط نیز در همان تراکنش دیتابیس بروزرسانی می‌شود.

در صورت نام کامل یا شماره مشترک، ثبت/ویرایش پاسخ ۴۰۹ با `detail.code=DUPLICATE_CUSTOMER` و `matches` برمی‌گرداند. هیچ داده‌ای در این مرحله ذخیره نمی‌شود. کاربر می‌تواند انصراف دهد یا همان درخواست را با `confirm_duplicate=true` تأیید کند. مشتری در حال ویرایش از بررسی تکرار خودش مستثنا است.

شماره‌ها شامل ارقام فارسی/عربی، فاصله، خط تیره و پیش‌شماره‌های `+98`/`0098` نرمال می‌شوند. شماره‌های ایران به قالب `0...` تبدیل می‌شوند. ترتیب شماره‌ها حفظ می‌شود؛ شماره تکراری در همان آرایه حذف می‌شود. حد شماره‌ها ۲۰ است و شماره واردشده باید ۷ تا ۱۵ رقم باشد.

حذف در UI ابتدا تأیید می‌گیرد و سپس ۱۰٬۰۰۰ میلی‌ثانیه بر اساس زمان سپری‌شده منتظر می‌ماند. هیچ DELETE قبل از پایان این مهلت ارسال نمی‌شود. Escape، کلیک Overlay و دکمه لغو در این مهلت حذف را لغو می‌کنند؛ هنگام اجرای درخواست DELETE، بستن Modal غیرفعال می‌شود. تب پس‌زمینه می‌تواند اجرای callback را به تأخیر بیندازد، ولی حذف زودتر از ۱۰ ثانیه رخ نمی‌دهد.

## آمار مالی

جداول سفارش و تراکنش مالی هنوز در پروژه موجود نیستند. `summary.available=false` و مقادیر صفر، نبود فعالیت ثبت‌شده را نشان می‌دهند؛ UI نیز این محدودیت را توضیح می‌دهد. نقطه اتصال محاسبات آینده `get_summary` در سرویس مشتریان است. تعداد سفارش، مجموع سفارش، پرداختی، بدهی و وضعیت در جدول مشتریان ذخیره نمی‌شوند و در Frontend محاسبه نمی‌شوند.

## تست

```sh
python3 -m unittest discover -s tests -v
python3 tests/serve_customers_fixture.py
```

تست‌های یکپارچه، خودشان سرور با پورت موقت و دیتابیس مستقل ایجاد و پاک‌سازی می‌کنند. محیط مرورگر نیز هیچ داده‌ای در دیتابیس اصلی وارد نمی‌کند. حساب آن فقط `customers-test` با رمز `test-password` است. برای خروج و پاک‌سازی محیط موقت Ctrl+C بزنید.

نه تست یکپارچه شامل حفاظت تمام Endpointها، سازگاری Auth و Members، ذخیره واقعی، اعتبارسنجی، جستجوی نام/کد/شماره و ورودی SQL، صفحه‌بندی، نرمال‌سازی شماره، انتقال شماره اصلی، حذف همه شماره‌ها، هشدارهای تکرار و تأیید، حذف واقعی و تولید کد هم‌زمان است.

در تست مرورگر، هدایت کاربر بدون ورود به Login، ثبت بدون شماره، چند شماره، ویرایش و انتقال شماره اصلی، پیام فیلدهای ضروری، هشدار نام/شماره و تأیید، جستجوی بی‌نتیجه، لغو تأیید حذف، لغو شمارش معکوس و حذف نهایی بررسی شدند. در عرض ۳۹۰ پیکسل overflow افقی وجود نداشت؛ در عرض ۱۴۴۰ پیکسل Sidebar و margin محتوا دقیقاً ۲۸۸ پیکسل بودند.

حالت خطای شبکه نیز با توقف سرور آزمایشی و انجام جستجو بررسی شد؛ پیام فارسی و دکمه تلاش مجدد نمایش داده شدند. Navbar مشترک در صفحات تنظیمات و حضور و غیاب نیز بررسی شد.

پس از پایان تست‌ها، محیط موقت متوقف و پروژه با `python3 start.py` و دیتابیس اصلی اجرا شد. جدول `customers` ایجاد شده و خالی است؛ حساب کاربری قبلی حفظ شده و بررسی Foreign Key هیچ خطایی نشان نداد. نشست آزمایشی در اجرای عادی نامعتبر تشخیص داده شد و به Login هدایت شد.

## به‌روزرسانی کارت‌ها و نمایش بیشتر

کارت‌ها با فاصله و padding کمتر و آمار افقی فشرده بازطراحی شدند؛ ارتفاع کارت معمولی در عرض ۱۴۴۰ پیکسل حدود ۱۴۰ پیکسل است. در موبایل، آمار در دو ستون نمایش داده می‌شود و overflow افقی وجود ندارد.

صفحه ابتدا حداکثر ۱۲ مشتری دریافت می‌کند. «نمایش بیشتر» هر بار با `limit=12` و offset بعدی درخواست می‌فرستد و نتایج را به کارت‌های موجود اضافه می‌کند. در پایان دکمه مخفی می‌شود. جستجو از دسته اول شروع می‌شود؛ ذخیره ویرایش و حذف، تعداد کارت‌های بارگذاری‌شده را تا حد موجودی جدید حفظ می‌کنند. خطای دریافت دسته بعدی، کارت‌های قبلی را حفظ می‌کند و امکان تلاش مجدد وجود دارد.

باگ popup ویرایش به دلیل z-index برابر فرم و جزئیات بود. لایه فرم اکنون ۹۰، جزئیات ۸۰ و هشدار تکرار ۱۰۰ است؛ فرم با Focus صحیح بالای جزئیات باز می‌شود و پس از بستن یا ذخیره، جزئیات قابل استفاده است.

تست نمایش بیشتر با ۲۵ مشتری فقط در دیتابیس موقت انجام شد: ۱۲ → ۲۴ → ۲۵ کارت، بدون شناسه تکراری؛ شروع مجدد جستجو از ۱۲ کارت و حفظ ۲۴ کارت پس از ذخیره ویرایش نیز تأیید شد.

```sh
python3 tests/serve_customers_fixture.py --backend-port 8001 --frontend-port 5502 --customers 25
```

این محیط آزمایشی در کنار اجرای عادی روی پورت‌های جدا اجرا می‌شود. بازنویسی آدرس API فقط در پاسخ سرور تست انجام می‌شود و تنظیمات یا نشست ورود اجرای عادی را تغییر نمی‌دهد. تعداد مشتری پیش‌فرض محیط تست همچنان صفر است.

## آخرین تماس با تاریخ شمسی

فیلد آخرین تماس در ثبت و ویرایش، تاریخ شمسی با قالب `۱۴۰۵/۰۷/۱۴` دریافت می‌کند. ارقام فارسی، عربی و انگلیسی، تاریخ بدون صفر اولیه ماه/روز و ورود هشت رقم مانند `۱۴۰۵۰۷۱۴` پشتیبانی می‌شوند. ورودی معتبر هنگام خروج از فیلد به نمایش فارسی و قالب سال/ماه/روز تبدیل می‌شود.

Frontend تاریخ را با جداکننده `/` ارسال می‌کند. Backend با کتابخانه موجود `jdatetime` صحت تاریخ و سال کبیسه را بررسی و سپس آن را برای ستون Date به تاریخ میلادی تبدیل می‌کند. خروجی API همچنان ISO است تا تاریخ‌های قبلی و سایر کلاینت‌ها سازگار بمانند؛ فرم ویرایش همان تاریخ ذخیره‌شده را شمسی نشان می‌دهد. API ورودی ISO قبلی را نیز می‌پذیرد. فیلد اختیاری است و خالی کردن آن تاریخ را حذف می‌کند.

تست جدید تبدیل `۱۴۰۵/۰۷/۱۴` به `2026-10-06`، ارقام عربی، روز کبیسه `۱۴۰۳/۱۲/۳۰`، رد `۱۴۰۴/۱۲/۳۰` و سایر روزهای نامعتبر، ذخیره واقعی، ویرایش و پاک کردن تاریخ را پوشش می‌دهد. هر ۹ تست یکپارچه و بررسی‌های نرمال‌سازی و نمایش Frontend موفق بودند.


## حذف مشتری دارای سابقه مالی

مشتری دارای تراکنش حذف‌نشده با ۴۰۹ و پیام فارسی دارای تعداد تراکنش‌ها رد می‌شود؛ ابتدا باید تراکنش‌ها در بخش مالی حذف شوند. کلاینت متن خطای رشته‌ای سرور را نمایش می‌دهد و آن را با خطای عمومی جایگزین نمی‌کند. پس از حذف همه تراکنش‌ها، حذف مشتری موفق است. مشتری بدون هیچ سابقه مالی طبق رفتار قبلی از جدول حذف می‌شود؛ مشتری دارای فقط تراکنش‌های حذف‌شده، با `deleted_at` از فهرست، جزئیات، جستجو، هشدار تکرار و انتخاب منابع جدید خارج می‌شود تا کلید خارجی و UUID درخواست‌های قبلی حفظ شوند. این رکورد سهمی در کد بعدی ندارد؛ کد آرشیوی داخلی منفی و کدهای نمایشی مشتریان باقی‌مانده از ۱۰۰۱ و بدون فاصله‌اند. هیچ تراکنش مالی با حذف مشتری از بین نمی‌رود یا دوباره قابل ثبت نمی‌شود. ستون جدید مشتریان هنگام راه‌اندازی بک‌اند برای دیتابیس قبلی اضافه می‌شود.

این رفتار با تست HTTP حذف مشتری دارای یک تراکنش حذف‌شده و یک تراکنش باقی‌مانده بررسی شد: خطای دقیق، سپس حذف موفق بعد از حذف تراکنش باقی‌مانده، عدم نمایش در جستجو/جزئیات/انتخاب منابع، جلوگیری از ارسال مجدد UUID، حفظ کلیدهای خارجی و شماره‌گذاری پیوسته. پیام فارسی سرور در مرورگر موقت هم تأیید شد.
