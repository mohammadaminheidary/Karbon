# ممیزی تکمیلی عملکرد Karbon — ۲۹ اکتبر ۲۰۲۶

این گزارش فقط تغییرات این نوبت را نسبت به working tree موجود هنگام ورود می‌سنجد. بهینه‌سازی‌های قبلی مشتریان، دفتر مالی، بانک و کد مرجع از ابتدا در baseline حضور داشتند؛ سود آن‌ها دوباره به این نوبت نسبت داده نشده است. گزارش قدیمی در README همین پوشه مستقل نگه داشته شده است.

FastAPI و SQLite، قرارداد کامل APIها، قواعد مالی/موجودی، مجوزها و الگوریتم چهره حفظ شدند. تمام خواندن‌ها و نوشتن‌های آزمون در دیتابیس ساختگی موقت بوده‌اند. فایل واقعی کاربر باز یا تغییر داده نشد. SHA-256 دیتابیس پایه در پایان دوباره کنترل شد:
`619f4dda422a0ea8ca3a1476e962ac97bb73daf57dbc4d71bd58c5fd0868d0b1`

## روش اندازه‌گیری

- Apple M4، macOS 27.2 arm64، ۱۰ CPU منطقی، RAM برابر ۱۶ GiB؛ Chrome 156.0.8078.73، Python 3.13.15، Node 24.19.0، SQLite 3.50.4، FastAPI 0.141.1، SQLAlchemy 2.0.54، Pydantic 2.13.5، Uvicorn 0.53.0، Tailwind 4.3.3، OpenCV 4.13.0. منطقه زمانی Asia/Tehran.
- داده ثابت: ۱۰۰۰ مشتری، ۱۰۰۰ سفارش، ۲۵۰ محصول، ۳۰۰۰ قلم سفارش، ۲۰۰۰ پرداخت مرتبط، مجموعاً ۵۴۰۰ تراکنش مالی، ۲۰ بانک، ۲۰۰۰ کار، ۳۰ عضو، ۹۰۰ حضور و ۲۰۰ سند. دیتابیس اصلی آزمون هیچ الگوی چهره‌ای ندارد؛ سنجش چهره در کپی مستقل با ۳۰ الگوی تصادفی رمزنگاری‌شده انجام شده است.
- APIها: یک worker بدون reload، ۳ گرم‌سازی + ۴۰ درخواست ترتیبی برای هر مسیر و هر حالت identity/gzip. زمان HTTP شامل دریافت و decode JSON در کلاینت Python و در حالت gzip شامل بازکردن فشرده‌سازی است. CPU هدر زمان فرایند سرور است. SQL شامل احراز هویت و BEGIN؛ زمان cursor شامل fetch/ORM/پردازش Python نیست. لاگ‌برداری SQL در هر دو سمت فعال است.
- مرورگر: headless Chrome، ۱۴۴۰×۱۱۰۰، بدون throttling، ۵ cold با context تازه و HTTP cache خاموش؛ warm شامل یک گرم‌سازی و ۵ نمونه با cache مشترک و تب تازه است. sessionStorage/API cache میان این تب‌ها مشترک نیست. cold به معنای پاک‌شدن OS page cache یا پردازش API نیست. startup در ۵ فرایند مستقل جدا سنجیده شد.
- ready رویداد karbon:page-ready است؛ visible یعنی ready + آماده‌شدن فونت‌ها + دو animation frame. content اولین کارت عدددار + دو frame است. این‌ها معیار عملی مرز رسم هستند، نه TTI استاندارد یا زمان اندازه‌گیری‌شده GPU. تعامل واقعی جدا با E2E بررسی شد. all widgets شامل پیمایش خودکار یکسان تا انتهای داشبورد و انتظار برای جزئیات/نمودارهاست؛ زمان رندر خالص نمودار نیست.
- قبل و بعد هر دو با CSS ساخته‌شده و سرور ثابت، بدون HMR/watch/reload اجرا شدند. pipeline اولیه بدون minify/hash/gzip بود؛ pipeline جدید production بخشی از تغییر اندازه‌گیری‌شده است. کنترل جدا با همان CSS بایت‌به‌بایت و همان سرور فایل اولیه انجام شده تا اثر کد از اثر pipeline قابل تفکیک باشد.
- request count درخواست cache را هم می‌شمارد؛ bytes مرورگر از CDP شامل انتقال شبکه است، اندازه JSON API جداست. TaskDuration/ScriptDuration/LayoutDuration/RecalcStyleDuration از CDP، heap از JSHeapUsedSize؛ RSS فقط فرایند API است، نه کل Chrome/GPU و نه peak. trace و CPU profile در اجرای جدا بعد از نمونه‌های زمانی گرفته شدند.
- heap نمونه لحظه‌ای بدون forced GC است؛ معادل حافظه retained یا اثبات نشت نیست. درصد مصرف کل CPU/GPU مرورگر و توان باتری سنجیده نشده است.
- abort مرورگر فقط کار/پاسخ منسوخ کلاینت را کنار می‌گذارد؛ تضمین توقف SQL در حال اجرای سرور نیست. کاهش درخواست تکراری با هماهنگ‌کردن شروع درخواست‌ها انجام شده است.
- میانه و IQR/min/max در JSON و CSV همراه‌اند. p95/p99 API با درون‌یابی خطی محاسبه شده؛ n=40 برای برآورد قابل اتکای دنباله تولید کم است. p99 مرورگر گزارش نمی‌شود. نمونه‌های بارگیری ناموفق از میانه زمان حذف، اما تعداد و جزئیاتشان مستقل گزارش شده است. زمان‌ها جمع‌پذیر نیستند؛ کار شبکه/اسکریپت/رسم همپوشانی دارد.
- کاهش = (قبل − بعد) / قبل × ۱۰۰؛ ضریب سرعت = قبل / بعد. علامت منفی یعنی پسرفت. این اعداد سنجش throughput یا تضمین روی سخت‌افزار دیگر نیستند.

شکست‌های حین کار پنهان نشده‌اند: bind اولیه زیر sandbox با PermissionError روبه‌رو شد و فقط سرورهای ساختگی با مجوز محیط اجرا شدند؛ race اعلان busy تنظیمات پس از lazy import اصلاح شد؛ CSS @import ابتدا 404 داشت، اصلاح و تست اختصاصی اضافه شد و اندازه‌گیری نسخه خراب کنار گذاشته شد؛ selector آزمون navigation میان دو لینک مشابه مبهم بود و به navbar محدود شد. این‌ها نتیجه نهایی ناموفق باقی نگذاشته‌اند. شکست‌های شبکه baseline جدا بالا ثبت‌اند.

## هزینه‌های باقی‌مانده و حدود نتیجه

بارگیری همه ویجت‌های lazy نسبت به واکشی یک پاسخ کامل، رفت‌وبرگشت/SQL اضافه دارد؛ هزینه کل و تغییر script/DOM/heap بالاتر دقیقاً در جدول داشبورد گزارش شده است. summary سریع‌تر به معنی سریع‌ترشدن تمام API کامل یا نوشتن‌ها نیست؛ همه پسرفت‌های منفی در جداول حفظ شده‌اند. با تغییر داده مرتبط، totals و جزئیات مرئی دوباره در یک درخواست snapshot می‌شوند.

پسرفت‌های قابل توجه دیگر: marker سرد انبار ۲۴٫۶ → ۲۶٫۸ms شده، هرچند visible آن سریع‌تر است؛ heap لحظه‌ای warm حضور ۱٫۷۱ → ۲٫۴۰MiB و محصولات تنظیمات حدود ۲٫۰۷ → ۲٫۴۷MiB است. چند هزینه اسکریپت تنظیمات نیز حدود ۸–۱۳٪ بالاتر است. این مقادیر حذف نشده‌اند؛ کاهش main thread یا انتقال به معنی بهبود تک‌تک معیارها نیست. نگه‌داشتن chunkهای قدیمی برای تب‌های باز هزینه دیسک دارد؛ پاکسازی نسخه‌های قدیمی پس از پایان عمر تب‌ها یک کار نگهداری باقی‌مانده است.

صفحه کارها هنوز ۲۰۰۰ کار و نمودار موجودی هنوز ۲۵۰ محصول را می‌خواند؛ virtualization/صفحه‌بندی با حفظ جستجو، keyboard و totals قدم بعدی قابل سنجش است. برای گزارش‌های فعلی precompute/materialized summary و برای الگوهای چهره cache جدید توجیه نشده‌اند. ظرفیت تحت بار همزمان، CPU/GPU کل مرورگر، اندازه‌گیری خالص هر SVG، دقت تشخیص واقعی، شبکه موبایل و زمان استاندارد TTI اندازه‌گیری نشده‌اند. proxy هم‌مبدأ بنچمارک preflight واقعی CORS را حذف می‌کند؛ CORS در تست launcher جدا بررسی شده است.
