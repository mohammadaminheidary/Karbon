# اندازه‌گیری و بهینه‌سازی کارایی Karbon — ۲۹ اکتبر ۲۰۲۶

FastAPI و SQLite حفظ شدند. تمام نوشتن‌ها در دیتابیس‌های ساختگی موقت انجام شد؛ دادهٔ واقعی کاربر استفاده نشد.

## روش و محیط

- مبنای پیش از تغییر: commit `416065af2351344243bcaacf72963017ead40110`؛ working tree هنگام شروع پاک بود. پروژه از ممیزی قبلی بازسازمان‌دهی شده و فرانت‌اند اکنون در `frontend/` است.
- یک فرایند Uvicorn، بدون reload؛ API مستقیم روی `127.0.0.1:8029`، سرور فایل/پراکسی آزمون روی `127.0.0.1:5529`. هیچ throttling یا فشرده‌سازی شبکه اعمال نشد.
- سخت‌افزار/نسخه‌ها در `results.json` ثبت شده‌اند؛ همهٔ اندازه‌گیری‌ها روی همین میزبان macOS انجام شده‌اند.
- داده: ۱۰۰۰ مشتری، ۲۵۰ محصول، ۱۰۰۰ سفارش، ۳۰۰۰ قلم سفارش، ۲۰۰۰ پرداخت متصل، مجموعاً ۵۴۰۰ تراکنش مالی، ۲۰ حساب بانکی، ۱۰ دستهٔ هزینه، ۲۰۰ سند/۴۰۰ ردیف مالی سند، ۵ حساب سند، ۲۰۰۰ کار، ۳۰ عضو و ۹۰۰ رکورد حضور. داده‌های تاریخ‌دار در بازهٔ ۹۰ تا ۱۲۰ روز تولید شده‌اند. قیمت اقلام سفارش می‌تواند با قیمت پیشنهادی محصول متفاوت باشد؛ این رفتار مجاز برنامه است.
- نسخهٔ ثابت `base.db` قبل از هر مرحله کپی شد. APIهای خواندن و مرورگر قبل از سناریوی نوشتن اجرا شدند. ثبت سفارش: ۴۳ درخواست با UUID تازه، ۳ گرم‌سازی و ۴۰ نمونهٔ ثبت‌شده؛ همه در دیتابیس موقت.
- هر مسیر API: ۳ گرم‌سازی، سپس ۴۰ درخواست ترتیبی؛ زمان دیواری شامل HTTP روی localhost است. p50 میانه است؛ p95/p99 با درون‌یابی خطی محاسبه می‌شوند و با این تعداد نمونه، به‌ویژه p99 برآورد دنبالهٔ بار واقعی نیست.
- SQL با eventهای SQLAlchemy شمارش شده است. `sql_ms` زمان cursor execution است و زمان کامل دریافت/تبدیل ردیف‌ها را پوشش نمی‌دهد. `cpu_ms` زمان CPU فرایند حین درخواست است؛ RSS یک نمونه پس از مجموعهٔ APIهاست، نه اوج مصرف.
- مرورگر Chrome headless، نمای ۱۴۴۰×۱۱۰۰؛ پنج بار cold با context تازه و HTTP cache غیرفعال، سپس یک گرم‌سازی و چهار نمونهٔ warm با HTTP cache مشترک. warm به معنای cache مرورگر است، نه cache مشترک API بین تب‌ها. سرور و cache سیستم‌عامل برای cold دوباره راه‌اندازی نشده‌اند.
- زمان آماده‌شدن: رویداد `karbon:page-ready`. زمان settled: آماده‌شدن صفحه و فونت‌ها به‌اضافهٔ دو animation frame. این‌ها جایگزین تعریف استاندارد TTI نیستند؛ قابلیت تعامل واقعی با آزمون سرتاسری کنترل شد.
- تعداد درخواست مرورگر از رویداد request محاسبه شده و درخواست‌های سرو‌شده از cache را نیز شامل می‌شود؛ بایت انتقال از CDP است. فایل نتایج شامل اندازه‌گیری تک‌تک نمونه‌هاست.

## نتایج API

تمام زمان‌ها میلی‌ثانیه‌اند. جهت تعداد SQL در ستون آخر «قبل ← بعد» است.

کاهش تأخیر = `(قبل − بعد) / قبل × ۱۰۰`؛ ضریب سرعت = `قبل / بعد`. همین فرمول برای تعداد اجرا و اندازهٔ پاسخ استفاده می‌شود. این نتایج، افزایش throughput را اندازه نمی‌گیرند.

پاسخ‌های کامل داشبورد، مشتریان، سفارش‌ها، مالی، حساب‌ها، فعالیت حساب و دفتر بانک پیش/پس از تغییر برابر بودند؛ فقط `generated_at` داشبورد در مقایسه نادیده گرفته شد. حجم JSON آن‌ها تغییر نکرد؛ داشبورد ۱۱۷۵۹۴ بایت است. انتخاب‌گر سبک عمداً قرارداد متفاوت دارد: فقط شناسه، کد، نام و تلفن؛ اندازه از ۳۸۵۱۹ به ۱۲۳۴۷ بایت رسید (کاهش ۶۷٫۹۵٪). API کامل مشتری همچنان حفظ شده است.

زمان ثبت سفارش حدود ۱۰٫۹٪ کمتر شد، اما تعداد SQL ثابت ماند و این مسیر بازطراحی نشده است؛ این اختلاف به‌تنهایی اثبات بهبود پایدار ثبت سفارش نیست. p95 مشتریان نیز بهبود نشان نداد؛ توزیع کامل در نتایج خام موجود است.

API داشبورد ۱۸ به ۱۷ اجرای SQL رسید (۵٫۵۶٪ کمتر)؛ میانهٔ تأخیر API حدود ۲٫۵۷٪ کمتر شد. اما زمان آماده‌شدن اولیه در اجرای نهایی سرد ۴٫۲۵٪ و گرم ۰٫۹۷٪ افزایش یافت. بنابراین هیچ ادعای سریع‌ترشدن بارگذاری اولیهٔ داشبورد مطرح نمی‌شود. بررسی زمان CPU مرورگر (حدود ۱۳۹ تا ۱۴۰ ms)، تعداد درخواست ثابت و انتقال تقریباً ثابت نشان داد کاهش کمتر از یک میلی‌ثانیه در API، عامل غالب این بارگذاری نیست. دو اجرای پس از تغییر نیز چند میلی‌ثانیه اختلاف داشتند؛ برای نتیجهٔ آماری، آزمایش‌های A/B طولانی‌تر لازم است. افزایش حدود ۱٫۳ کیلوبایت انتقال ناشی از کد اضافه‌شده ثبت شده و پنهان نشده است.

اثر تأییدشدهٔ تازه‌سازی: سه focus متوالی پیش‌تر سه درخواست و اکنون یک درخواست دارند (۶۶٫۶۷٪ کاهش). polling سی‌ثانیه‌ای در هر دو مرحله یک درخواست داشت. پاسخ مالی همچنان تازه گرفته می‌شود؛ فقط بازترسیم دادهٔ بدون تغییر حذف شده و جدول بستهٔ نمودار هنگام بازشدن ساخته می‌شود. ۱۲ نمودار، ۱۸ ویجت، نبود خطای JS/HTTP و نبود overflow در عرض ۳۹۰ در اندازه‌گیری‌های قبل/بعد تأیید شد.

## تغییرات

- مشتریان: تجمیع آمار در پرس‌وجوی فهرست و endpoint جست‌وجوشونده/صفحه‌بندی‌شدهٔ `/api/customers/options`؛ انتخاب‌گرهای سفارش و مالی از پاسخ سبک استفاده می‌کنند. انتخاب‌گرهای native مالی هنوز همهٔ گزینه‌ها را صفحه‌به‌صفحه دریافت می‌کنند تا رفتار UI تغییر نکند.
- سفارش‌ها: بارگذاری گروهی مشتریان، اقلام و پرداخت‌های صفحه؛ قرارداد خروجی حفظ شد.
- مالی/اسناد: یک دریافت گروهی ارتباط فاکتورها و یک تجمیع پرداخت برای پاسخ، به‌جای جست‌وجوی هر ردیف.
- بانک: محاسبهٔ مجازبودن حذف از تجمیع موجود؛ گزارش یک حساب فقط همان حساب را می‌خواند.
- داشبورد: محاسبهٔ بدهی و سررسید در یک پرس‌وجو؛ ادغام خواندن‌های هم‌زمان برای بازهٔ یکسان؛ تغییر داده حین دریافت، دریافت تازهٔ بعدی را حفظ می‌کند؛ بازترسیم بدون تغییر حذف شد.
- بازشماری: فقط شماره‌های تغییریافته به‌روزرسانی می‌شوند؛ اجراهای دسته‌ای و دو مرحلهٔ امن برای یکتایی کد مشتری حفظ شدند. در نسخهٔ موقت بدون تغییر: ۶۵٫۳۰ → ۲٫۱۷ ms؛ پس از ایجاد شکاف: ۶۸٫۶۵ → ۹٫۶۹ ms؛ هشت تکرار برای هر حالت. در اجرای دسته‌ای شمارش event نشان‌دهندهٔ فراخوانی cursor است، نه تعداد ردیف‌های تغییرکرده.
- ایندکس: تنها ایندکس جزئی `(bank_id, transaction_date, transaction_time, id) WHERE deleted_at IS NULL` اضافه شد. طرح قبل از ایندکس نیازمند temporary B-tree برای ترتیب بود؛ بعد از آن ترتیب با همان ایندکس تأمین شد. ایندکس‌های حدسی دیگر اضافه نشدند. هزینهٔ بلندمدت نوشتن هنوز اندازه‌گیری نشده است.

## آزمون و کار باقی‌مانده

- بک‌اند: ۱۱۱ آزمون اجرا، ۱۱۰ موفق و یک آزمون اختیاری تصاویر واقعی چهره اجرا نشد.
- Python فرانت‌اند: ۱۰ موفق؛ Node: ۶۷ موفق.
- آزمون سرتاسری داشبورد: موفق؛ جمع‌های واقعی، بدهی/موجودی، نمودار/جدول، فیلتر، صفحهٔ موبایل، تغییر داده بین تب‌ها، polling، خطا/تلاش مجدد و رقابت پاسخ‌ها بررسی شد. نقص اولیهٔ زمان‌بندی جدول lazy با ساخت هم‌زمان در کلیک summary رفع و دوباره آزمون شد.
- آزمون دریافت داده: موفق؛ cold/warm، ادغام GET، ابطال پس از تغییر و refresh دستی.
- آزمون مستقل بازیابی صفحات: اجرای نهایی هر ۱۴ سناریو موفق شد؛ محتوای موجود در refresh کند/ناموفق حفظ شد و بازیابی اولیه بررسی شد. چند اجرای قبلی در مسیرهای متفاوت خطای بارگیری entry JavaScript داشتند؛ نسخهٔ مبنا و تکرار نهایی نسخهٔ جدید موفق بودند. منشأ این خطای متناوب قطعی نشده است و نباید نتیجهٔ آخر را تضمین نبود خطای متناوب دانست.
- پروفایل چهره فقط شامل بارگذاری مدل و ۱۰ تصویر خاکستری بدون چهره بود: بارگذاری اولیه حدود ۱۰۰ ms و راهنمای بدون چهره حدود ۶٫۳۰ ms در مبنا. این بنچمارک تشخیص واقعی، دقت، تعداد اعضای زیاد یا دوربین هم‌زمان نیست؛ کد چهره تغییر نکرد.
- ابطال هدفمند کش، تغییر صفحه‌بندی عمومی، کاهش جزئیات قرارداد سفارش و بازطراحی تراکنش‌ها به این تغییر اضافه نشدند: اثر مستقل کافی برای آن‌ها اندازه‌گیری نشد و حذف جزئیات/کوتاه‌کردن نادرست تراکنش می‌تواند رفتار یا صحت مالی را عوض کند. وابستگی، زیرساخت و دیتابیس جدید اضافه نشد.

## بازتولید

ابزارهای تشخیصی در `backend/tests/performance/` هستند و همان روش این اجرا را حفظ می‌کنند. وابستگی‌های برنامه باید از قبل موجود باشند؛ Playwright/Chrome موجود استفاده می‌شوند. psutil اختیاری است و فقط نمونهٔ RSS را فراهم می‌کند.

```sh
export KARBON_PERF_DIR="$(mktemp -d /private/tmp/karbon-perf.XXXXXX)"
export KARBON_DATABASE_PATH="$KARBON_PERF_DIR/base.db"
export KARBON_JWT_SECRET=isolated-performance-only
export PYTHONDONTWRITEBYTECODE=1
python3 -B backend/tests/performance/seed.py
python3 -B backend/tests/performance/run.py after
# در ترمینال دوم، با همان KARBON_PERF_DIR:
python3 -B backend/tests/performance/bench.py after
KARBON_PLAYWRIGHT_PATH=/path/to/existing/playwright KARBON_CHROME_PATH=/path/to/existing/chrome node backend/tests/performance/browser.cjs after
python3 -B backend/tests/performance/writes.py after
python3 -B backend/tests/performance/selector.py after
python3 -B backend/tests/performance/face.py after
# Ctrl+C فقط سرورهای همین fixture را متوقف می‌کند.
```

برای مقایسهٔ نسخه‌های کد، یک کپی مستقل از مبنا و یک کپی از نسخهٔ نهایی را با همان `base.db` و تنظیمات اجرا کنید؛ برچسب before/after به‌تنهایی نسخهٔ کد را تغییر نمی‌دهد. پورت‌های ۸۰۲۹ و ۵۵۲۹ باید آزاد باشند. نمونه‌های تصویری و نتایج خام در محیط موقت نگهداری شدند؛ توکن‌های آزمایش در مخزن کپی نشده‌اند.
